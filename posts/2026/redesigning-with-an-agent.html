Coding Stuff Has a New Look

2026-09-15 · 12 min read
  • #announcement
  • #design
  • #ai
  • #opinion

If you have visited Coding Stuff before, you may notice that things look a little different. Since 2020, this blog had been running on a third-party theme. It worked, but reading on it never quite felt right.

So I drew a wireframe of what it should be and rebuilt the site from it, as a Jekyll theme of its own: lofy, as in lo-fi. This post walks through what has changed and why, and then takes a short detour into what building it with an AI agent taught me.

Reading

The idea behind the new design is simple: everything on the page should either help you read or get out of the way.

  • Distraction-free. There are no cover images or decorations between you and the first paragraph. The only images in a post are the ones that explain something.
  • Images you can look at closely. Each image has a short caption underneath. Click one, like the one above, to open it larger; click it again to zoom in and drag around, and click the dark background to put it back.
  • Type does the work. Headings and body text are set in Newsreader, a serif designed for reading on screens. The interface uses Inter, and code uses JetBrains Mono. All three come from Google Fonts, so the site looks the same on every device.
  • A quiet structure. The sidebar holds only what you need to find your way around, and nothing else.

Settings

A small customise button at the top of the page opens two settings.

  • Theme can be set to auto, light or dark. Auto is the default and follows your system, even when it switches while you are reading; light and dark are remembered.
  • Focus reading is available on posts and the About page on a desktop. It hides the sidebar and lets the header and footer fade back, leaving only the article. The layout slides into place rather than fading, so you can see where things went.

Both settings use text labels rather than icons. A reader should be able to read what a control does, not decode a symbol.

Navigation

  • On this page. Posts with headings get a table of contents. On wide screens, it sits expanded beside the article, so you always know where you are, marks the section you are reading, and scrolls on its own when the list is longer than the window. On smaller screens, it is a collapsible block above the text.
  • Continue reading. Every post ends with up to five posts to read next: the next and previous posts first, followed by others that share a tag. A small label says why each one is there, such as previous post or also in #swift. When you finish an article, the best next read is often one about the same subject, not simply whatever came out next.
  • Link previews. Hovering over a link to another post shows a small card with its date, title and summary, so you can decide whether to follow it without losing your place. Try it on the post about inout. It doesn’t appear on touch screens, where there is no hover.
  • Heading anchors. Hovering over a heading reveals a # in the left margin, so you can link straight to a section while the heading itself stays aligned with the text.
  • Tags and archive. Every post can be found by tag on the tags page, or by year in the archive.
  • Cleaner addresses. Post URLs are shorter and no longer end in .html. Old links still work.

Mobile

A phone is often where someone first lands on a post, usually from a link, so the small-screen layout makes its own decisions rather than squeezing the desktop one.

  • Posts start with the post. Below the site title comes the article itself. The links to the rest of the site wait at the end, after continue reading: someone arriving from a link came for this article, and looking around is what they do once they have read it.
  • Pages start with the navigation. On the home page, About, Tags and Archive, a single quiet row of links sits under the site title, and the page you are on is simply darker and bolder. That row already names the page, so its title isn’t repeated below it.
  • Nothing depends on hovering. Link previews stay out of the way on touch screens, the table of contents folds into a block above the text, and a zoomed-in image moves under your finger.

Sharing

When a post is shared in a chat app or on social media, its preview now shows that post rather than one generic card for the whole blog: its title, date and tags, set in the same type as the site.

Each of these images is made when the site is built, so a new post gets its own without any extra work, and a long title simply shrinks to fit.

Code

Most posts here contain code, so code blocks received the most attention. The question behind each change was the same: what is the reader going to do with this? Rather than describe them, here they are.

A code block can carry a label showing which file it belongs to, and highlight the lines that matter:

enum Theme: String, CaseIterable {
    case auto, light, dark

    var label: String { rawValue.capitalized }
}

When code changes, the old and new lines can be shown together. Removed lines are marked in red and added lines in green. Try the copy button: it leaves the removed lines out, because you want the code as it is now, not the diff.

struct SettingsView: View {
    @AppStorage("isDarkMode") private var isDarkMode = false
    @AppStorage("theme") private var theme = Theme.auto

    var body: some View {
        Toggle("Dark Mode", isOn: $isDarkMode)
        Picker("Theme", selection: $theme) {
            ForEach(Theme.allCases, id: \.self) { Text($0.label) }
        }
        .pickerStyle(.segmented)
    }
}

Terminal commands get a terminal frame. Copying them leaves out the $ prompts, because nobody wants to paste a prompt into their terminal.

$ swift build
$ swift run

Program output has its own frame and no copy button, because nobody copies output. When it belongs to the code above it, the two are joined into one card:

let themes = Theme.allCases.map(\.label)
print(themes.joined(separator: " / "))

Auto / Light / Dark

Errors tint the whole block, so you can tell something went wrong before reading a single word. This one comes from the inout post:

var number = 0

func addOne(_ value: inout Int) {
    print(number)
    value += 1
}

addOne(&number)

Simultaneous accesses to 0x106344130, but modification requires exclusive access.

A compiler or runtime message mentioned on its own gets a small diagnostic card instead, for errors and warnings alike:

Cannot assign to value: 'theme' is a 'let' constant

Variable 'result' was never mutated; consider changing to 'let' constant

Examples of input and output, such as a problem’s sample case, sit side by side:

Input
[8,1,2,2,3]
Output
[4,0,1,1,3]

A note sets an aside apart from the text, such as a caveat or a bit of background, so the explanation around it keeps its flow:

In the SwiftUI introduction, a note like this one explains why two equal numbers in a list can get their rows mixed up.

And quotes can credit their source, as you will see in a moment. Finally, the one sentence a post comes down to can go into a takeaway card. This post has one near the end.

The older posts have been updated to use them where they fit, so their code, output and conclusions read the same way.

Built with an AI Agent

I am an iOS developer, not a web developer, and most of the code behind this redesign was written by an AI coding agent. That deserves a few honest words, because it was neither as magical nor as disappointing as people tend to expect.

Where it helps. An agent is useful for turning a clear intention into working code, especially in a stack you don’t use every day. It can look things up, follow conventions consistently, write tests, and keep documentation in sync.

Where it doesn’t. It only knows what you tell it. It cannot tell whether a page feels right, whether a control is obvious, or whether a layout works on the device in your hand. It tends to add rather than remove. And it isn’t free: every unclear request costs another round of work.

In other words, the agent made building the site much faster. It did not make any of the decisions above for me.

So What Counts as a Chore?

In my last post, I wrote:

We only ask AI to do the things we don’t want to do.

So Are We Bound to Be Replaced by AI?

A project like this makes that sentence much less simple than it sounds.

This is where I think my last post blurred two questions together: is this boring? and is this indispensable? Checking that the result works is boring, but indispensable. Deciding what a product should feel like is neither boring nor dispensable. Looking things up is boring and, most of the time, safe to hand over.

And the answers differ from person to person. A designer who loves CSS may find implementation the best part of the job. A researcher may enjoy the digging more than anything else. For me, it depends on the project.

Why ‘Being Replaced’ Is No Longer the Point

This is why I think will AI replace us? is slowly becoming the wrong question.

It assumes that a job is a fixed bundle of tasks, and that AI either takes the bundle or it doesn’t. But the line between chore and non-chore doesn’t run between jobs. It runs through the middle of every job, and it runs through a different place for every person.

AI doesn’t take a job. It takes whatever we hand to it. Hand over the chores, and you get more time for the parts that matter. Hand over the indispensable parts because they are boring, or the parts you enjoy because AI happens to be faster, and you have replaced yourself. If that comes down to laziness, AI was never the threat: anyone willing to do those parts properly could have taken your place long before it arrived.

So the more useful question is:

Which parts of your work are actually yours?

Living with AI

Whether you are excited about AI or still a little doubtful — as I am — a few suggestions:

  • Know your own map. For each part of your work, ask both questions: is it boring, and is it indispensable? Don’t borrow someone else’s answers.
  • Delegate the work, not the accountability. You can hand over checking, but not the responsibility for what you ship.
  • Protect the parts you enjoy. They are often the reason you do this work at all.
  • Start from the product, not the technology. Building something to show off a technology and then looking for a use for it is a poor strategy. Start from what users need, then find, use, or even create the best technology for it.
  • Be clear before you ask. Delegating isn’t free, and knowing what you want is the cheapest way to get it.

Conclusion

The new Coding Stuff is quieter, easier to read, and much kinder to code. I hope it makes the posts here more pleasant to spend time with.

Building it with an agent didn’t convince me that AI will replace developers, nor that it won’t. It convinced me that the question matters less than knowing which parts of the work we should never hand over.
